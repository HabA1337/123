## 2. Что входит в «один модуль»

Разбор исходного ТЗ по смыслу, не по формулировкам.

### 2.1. Остатки и приёмка онлайн для клиента, по ячейкам

Клиент в веб-кабинете видит приёмку в онлайне: какой товар принят, в какую ячейку положен, сколько доступно. Склад на ТСД принимает по ШК, кладёт в ячейку, остаток сразу появляется у клиента.

Входит:

- документ приёмки (план / факт / расхождения);
- адресное хранение: зона → ряд → стеллаж → полка → ячейка;
- ТСД: сканирование товара и ячейки, частичная приёмка, фото/комментарий при браке;
- веб-кабинет клиента: остатки по ячейкам, история приёмки, онлайн-статус текущей приёмки;
- роли: клиент видит только свои товары, склад — операционку.

### 2.2. Отгрузки FBS: заказы в одном месте, заявка на город

Система сама забирает новые сборочные задания WB API, складывает их в одну складскую заявку **на каждый город/склад отгрузки** и выдаёт на ТСД как одно задание.

Входит:

- обмен с WB Marketplace API v3: новые заказы, статусы, поставки (`supplies`), перевод в доставку;
- группировка: кабинет WB → склад ВМС → город/офис приёмки WB;
- складская «заявка на сборку» (волна): список заказов, ячеек, штук;
- очередь и назначение сборщиков;
- исключения: нет товара, брак, отмена WB, перенос в следующую волну.

### 2.3. Онлайн-мониторинг заявки и ТСД

Диспетчер на вебе видит процент сборки заявки и живой поток действий с терминалов.

Входит:

- прогресс заявки: собрано / всего, % по заказам и по штукам;
- живая лента ТСД: кто, какой заказ, какой ШК/КИЗ, ячейка, ошибка, простой;
- статусы сборщика: в работе / пауза / нет связи;
- тайминги: начало, среднее время на заказ, узкие места.

### 2.4. Кнопка «в доставку»

После 100% сборки заявки кнопка отправляет заказы в доставку WB. Технически это поставка WB: заказы уже в `supply`, затем `PATCH /api/v3/supplies/{id}/deliver`. Перед кнопкой система проверяет метаданные (КИЗ и пр.), иначе WB отвечает 409 и поставка не уходит.

### 2.5. КИЗ → стикер WB

На сборке сотрудник сканирует ШК товара, затем КИЗ. По КИЗ система понимает, какой стикер WB клеить на это вложение. Отдельная вкладка в ТСД и в вебе: повторное сканирование КИЗ печатает тот же стикер (переклейка, потеря, контроль).

Входит:

- связка заказ WB ↔ товар ↔ КИЗ (SGTIN) ↔ стикер WB;
- передача КИЗ в WB: `PUT /api/v3/orders/{id}/meta/sgtin`;
- получение стикера: `POST /api/v3/orders/stickers` (PNG / ZPL);
- вкладка «СТИКЕР» в ТСД и в веб-интерфейсе;
- запрет печати стикера, если КИЗ не прошёл проверку или не привязан к заказу.

### 2.6. Мост ТСД — ВМС — принтер

ТСД сам стикер не рисует. Терминал отправляет событие «напечатать стикер заказа N / КИЗ X» в ВМС. ВМС забирает макет у WB (или кэш) и ставит задание в очередь печати. Служба-мост отдаёт ZPL/PNG на конкретный принтер.

Входит:

- очередь печати, приоритет, повтор, отмена;
- привязка принтера к зоне / столу / сборщику;
- статусы: принято / на принтере / ошибка / нет бумаги;
- драйвер RAW:9100 (Zebra/TSC) или CUPS;
- журнал: кто, когда, какой КИЗ, какой стикер, какой принтер.

### 2.7. Продажа на WB → минус в ВМС

Чтобы не продавать в ноль: при продаже/выкупе на WB остаток в ВМС уменьшается автоматически, резерв по открытым заявкам учитывается отдельно.

Входит:

- источник факта продажи: статусы FBS + отчёт реализации / продажи (уточняется на старте);
- списание с ячейки или с виртуального остатка клиента;
- резерв под открытую сборку, чтобы две волны не взяли одну штуку;
- защита от двойного списания (сборка уже списала, продажа не списывает второй раз);
- алерт, если WB продала больше, чем есть в ВМС.

## 3. Как это работает в одном контуре

```text
Клиент (веб)          Склад (веб-диспетчер)         ТСД
   │                         │                       │
   │  видит ячейки/приёмку   │  заявка по городу %   │  ШК → КИЗ → стикер
   │                         │  лента ТСД            │
   └─────────── ВМС ─────────┴───────────────────────┘
                  │
      ┌───────────┼────────────────┐
      │           │                │
  WB API      Мост печати     Очередь событий
  заказы      Zebra/TSC       остатки / резервы
  стикеры
  supply.deliver
  meta/sgtin
  продажи → списание
```

Сборка одного заказа на ТСД:

1. Открыл заявку города.
2. Подошёл к ячейке, сканировал ячейку.
3. Сканировал ШК товара.
4. Сканировал КИЗ.
5. ВМС сверила товар, ячейку, КИЗ, заказ WB.
6. Мост напечатал стикер WB.
7. Сотрудник клеит стикер, заказ в заявке +1.
8. На 100% заявки диспетчер жмёт «в доставку».

## 5. Допущения, без которых фикс не держится

1. Есть рабочая ВМС: номенклатура, ШК, пользователи, остатки, API или возможность встроить модуль.
2. Есть приложение ТСД (Android, 2D-сканер) и доступ к его коду или SDK для двух вкладок: сборка и стикер.
3. Один склад, одно юрлицо, один кабинет WB, до трёх городов отгрузки.
4. Принтеры этикеток с ZPL (Zebra / TSC / аналог), сеть до них с ВМС, не «печать через облако неизвестного вендора».
5. WB отдаёт стикер только в статусах «на сборке» / «в доставке» — заказы вовремя переводятся в нужный статус.
6. Маркировка в рамках FBS: сканирование КИЗ и `sgtin` в заказ. Полный ГИС МТ (эмиссия, агрегация, вывод из оборота через True API «Честного знака») — отдельно.
7. «Продажа на WB» = согласованный источник (статус заказа и/или отчёт реализации). Возвраты и оспаривания — отдельным правилом, не «магией».
8. Нагрузка пилота: до 2 000 заказов FBS в сутки, до 20 ТСД, до 5 принтеров.
9. Заказчик даёт: токен WB, тестовые заказы, 2–3 дня доступа на складе, ответственного технолога.
10. API WB лимитирован (~300 запросов/мин на кабинет). Очереди и кэш стикеров закладываем, но «мгновенно при 10 кабинетах» — другой объём.

Если пункт 1 или 2 не выполнен (нет ВМС или нет ТСД-приложения) — считать сценарий «с нуля», не эту цену.

## 6. Что не входит

- ТСД, принтеры, стойки, Wi-Fi склада, сервер;
- Ozon / Яндекс Маркет / FBO / DBS;
- полноценный контур «Честный знак» (СУЗ, агрегация коробов, вывод из оборота);
- биллинг клиентов фулфилмента, договоры, акты, тарификация ячеек;
- видеоконтроль ячеек, голосовой отбор, роботизация;
- iOS-ТСД;
- больше одного склада / мультикабинет WB без отдельной оценки;
- абонентская поддержка после 30 дней гарантии.

## 7. Риски, которые двигают срок, а не «проглотятся внутри»

| Риск | Зачем он важен | Как закрываем |
|---|---|---|
| WB часто меняет API и валидацию meta | Кнопка «в доставку» падает с 409 | Проверка `metaDetails` до кнопки; сопровождение |
| КИЗ со служебными символами GS | Стикер печатается не на тот заказ | Нормализация DataMatrix, запрет дублей |
| Стикер WB ещё не готов | Пустая печать, простой линии | Кэш, повтор, статус на ТСД |
| Печать по Wi-Fi | Классический отказ «моста» | Локальная очередь, RAW 9100, журнал |
| Двойное списание | Собрали и ещё «продажа» списала | Один источник истины остатка + резерв |
| Нет ячеек в текущей ВМС | Приёмка «по ячейкам» некуда вешать | Сначала адресная модель, иначе +2–3 недели |

## 8. Сравнение с рынком (чтобы цифра не висела в воздухе)

Готовый SaaS-WMS с WB/КИЗ/ТСД (Целиком, MPFIT и аналоги) — **40–125 тыс. ₽/мес**, внедрение 2–4 недели, но процессы склада подгоняются под коробку.

Типовой коннектор 1С ↔ WB без волн, живого мониторинга ТСД и print-моста — **80–250 тыс. ₽**.

Кастом «как у Константина» (кабинет клиента + волна по городу + ТСД-мониторинг + КИЗ→стикер + мост + автосписание) коробочным коннектором не закрывается. Отсюда фикс **1,25–1,85 млн ₽**, а не «как модуль 1С за 150 тысяч».

## 9. Что нужно от Константина, чтобы не сдвинуть срок

1. Стек текущей ВМС и ТСД (язык, есть ли API, кто владеет кодом).
2. Модель ячеек уже есть или её делать.
3. Сколько складов, кабинетов WB, городов, ТСД, принтеров.
4. Модели принтеров и как они сейчас печатают.
5. Категории с КИЗ и нужен ли сразу ГИС МТ.
6. Что считать «продажей»: выкуп, переход в доставку, отчёт реализации.
7. Нужен ли кабинет клиента в первой очереди или можно второй очередью.
